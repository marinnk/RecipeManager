# フロントエンドコードを読むためのメモ（自分用）

レシピ登録画面（`frontend/src/app/recipes/new/`）を読んだときに出てきた、Reactの実装で何度も繰り返し出てくる書き方のパターンをまとめたもの。忘れたらここを見返す。

## パターン1: `useState`のペア

```ts
const [title, setTitle] = useState("");
```

- `title` … 今画面が覚えている値そのもの
- `setTitle` … その値を書き換えるための専用の関数

`setTitle(...)`を呼ぶと値が変わり、画面が自動で描き直される。ただの変数に代入するだけでは画面は更新されない。

## パターン2: `value` + `onChange` のセット

入力欄には必ずこの2つがセットで書かれている。

```tsx
<input
  value={title}                              // 表示する内容＝覚えている値
  onChange={(e) => setTitle(e.target.value)} // 打たれるたびに覚えている値を更新
/>
```

片方だけでは動かない（表示だけで入力を反映できない、または反映だけで表示に出ない）。

## パターン3: `map`で一覧を描く

```tsx
{tags.map((tag) => (
  <span key={tag}>{tag}</span>
))}
```

配列の中身を1つずつ、画面のパーツに変換している。Javaの`stream().map()`に近い。

## 登録ボタンを押したときの流れ（全体像）

```
画面（RecipeRegisterForm）
  → 橋渡し役（useCreateRecipe）
    → 通信担当（lib/api/recipes.ts）
      → next.config.tsの転送設定
        → バックエンド（Spring Boot）
```

わからなくなったら、この順番でファイルを開いて追いかけると迷わない。

## コードを読むときに見る3点セット

1. **役目** … このファイルは何のためにあるか
2. **中身のメソッドの意味** … `useState`や`setTitle`が何をしているか
3. **繋がり** … それらのファイル・処理がどんな順番で呼び合っているか（上の全体像図）

これに加えて「**なぜその作りにしたか**」を説明できると、理解として一段深くなる。

## なぜその実装にしたか（登録画面の例）

- **なぜ通信処理（`lib/api/recipes.ts`）とフック（`hooks/useCreateRecipe.ts`）を分けたか**
  → CLAUDE.mdの方針。前回のSpring Boot課題で「Controllerを薄くしてServiceに処理を寄せる」のと同じ考え方をフロントエンドにも適用したもの
- **なぜ`next.config.ts`で転送設定（rewrites）を使い、バックエンドのURLを環境変数で渡す方式にしなかったか**
  → 本番では CloudFront が `/api/...` を自動でバックエンドに振り分ける設計（基本設計書）。ローカル開発でも同じ動き方を再現しておけば、フロントエンドのコード自体は本番用に書き換える必要がなくなる
- **なぜReact Queryのような専用ライブラリを使わず、`useState`で自分で書いたか**
  → 今のところ送信処理は1つしかなく、ライブラリを入れるほどの複雑さがない。「単一の責務に絞る」「必要になるまで増やさない」という方針に沿った判断
- **なぜタグの追加・削除のロジックをフックに分離せず、画面のコンポーネント内に書いたか**
  → タグの追加・削除はバックエンドと通信しない、画面内だけの一時的な操作。フックに分けるのは「API通信のロジック」だけというルールに沿うと、ここは分けなくてよい

## なぜその実装にしたか（一覧画面の例）

- **なぜ`useEffect`を使ったか**
  → 登録画面の送信処理（`useCreateRecipe`）はボタンを押した瞬間に動けばよかったが、一覧は画面が開いた瞬間に自動でデータを取得する必要がある。「ユーザー操作で動く」か「表示された瞬間に自動で動く」かの違いが、`useState`だけで足りるか`useEffect`が要るかの違いになっている
- **なぜ`isLoading` / `error` / `recipes`の3つの状態に分けたか**
  → 「読み込み中」「失敗した」「0件だった」「表示するデータがある」の4パターンを画面に出し分ける必要があり、そのために最低限必要な情報がこの3つだった。1つの`state`にまとめず分けたのは、それぞれ意味が違う値だから（「読み込み中かどうか」と「取得したデータ」は別の概念）
- **なぜ一覧取得の関数（`getRecipes`）を、登録の関数（`createRecipe`）と同じ`lib/api/recipes.ts`に書いたか**
  → どちらも「レシピに関する通信」という同じ役割のファイルなので、ここでファイルを分けると関連する処理が散らばってしまう。「単一責務」は機能ごとではなく「役割（通信）」単位で考えている
- **なぜ`RecipeRepository`に`findAllByOrderByCreatedAtDesc()`という専用メソッドを足したか**
  → Spring Data JPAはメソッド名からSQLを自動生成してくれるため、自分でSQLや並び替えのコードを書かずに済む。「新しい順で返す」という要件をメソッド名だけで表現できる
- **なぜControllerにテストを書かず、Serviceだけテストしたか**
  → CLAUDE.mdの「サービス層の単体テストを書く」という方針、かつ既存のRecipeController・RecipeServiceにもControllerテストの前例が無かったため、既存パターンに合わせた
- **なぜモックアップでは`/recipes`だった一覧画面を、トップページ（`/`）に実装したか**
  → 登録フォームが登録完了後に`router.push("/")`していた（＝元々トップページに戻る前提で作られていた）ことと、トップページがまだ使われていないプレースホルダーだったことから、実装時に`/recipes`ではなく`/`に合わせる判断をした
