# 用語集（インフラ・クラウド関連）

[docs/basic-design.md](./basic-design.md) を読むときに出てくる、インフラ・クラウド系の用語をまとめたもの。分からなくなったらここに戻ってくる。

## コンテナ（Docker）

アプリケーションと、それを動かすのに必要なもの（ライブラリ・設定など）をひとまとめにして、独立した「箱」として動かす技術。仮想マシン（VM）と似ているが、OSを丸ごと動かすVMと違い、ホストのOSを共有しつつプロセスやファイルシステムだけを分離するので軽量で起動が速い。

このプロジェクトでは「Next.jsコンテナ」「Spring Bootコンテナ」を、同じEC2上に並べて動かしている（§2）。

- **同じEC2にまとめる利点**: EC2は起動時間で課金されるため、1台にまとめると台数分の費用がかからない。コンテナ同士の通信もシンプルになる
- **別々のEC2に分ける場合の欠点**: EC2代が単純に倍になる上、どちらに振り分けるかを判断する装置（ALB等）が必要になりがち
- （本格的な本番サービスでは逆に「分ける」ことで独立してスケールできる、障害の影響範囲を分けられる、というメリットが重視される。今回は学校課題規模なのでコストとシンプルさを優先）

## セキュリティグループ

AWS上の各リソース（EC2・RDSなど）につける**仮想的なファイアウォール**。「どこから」「どのポートへ」の通信を許可するかをルールとして設定し、それ以外は問答無用で拒否する。

たとえるなら、マンションの荷物用搬入口が**建物専用の私道（EC2からの通信）を通ってきた配送車だけ**通れるようになっていて、公道（インターネット）から直接来た人はそこにたどり着けない、というイメージ。「暗証番号を知っているか」ではなく「どの経路から来たか」で機械的に判定する。

このプロジェクトでは、RDSのセキュリティグループを「EC2からの3306番ポートのみ許可」としている（§2）。

※ セキュリティグループを通過した後に必要な「DBのユーザー名・パスワード」は別の話（§6）。こちらはオートロックの部屋番号入力に近い、「正しい鍵を持っているか」の確認。セキュリティグループ＝経路の制限、DB認証＝鍵の確認、の2段構え。

## NAT Gateway

外部から直接アクセスできない「プライベートサブネット」内のサーバーが、外部インターネットに通信しに行くための中継装置。使うと時間課金＋通信量課金の固定費がかかる。

このプロジェクトではEC2を外部から直接アクセスできる「パブリックサブネット」に置くため使わない（§7）。

## マルチAZ構成

RDSを複数のAZ（Availability Zone＝独立したデータセンターの単位）に自動複製し、片方が落ちても自動切替できるようにする機能。冗長化できる代わりに費用がほぼ倍になる。

このプロジェクトでは「片方が落ちたら止まる」リスクを許容して使わない（§7、§9）。

## ALB（Application Load Balancer / ロードバランサー）

複数台のサーバーにアクセスを振り分ける装置。時間課金の固定費がかかる。

このプロジェクトではEC2が1台だけなので不要。CloudFrontから直接EC2に転送することで固定費を節約している（§2、§7）。

## VPC・サブネット

- **VPC**: AWS上に作る仮想的なネットワーク区画（自分専用の「区画」を用意するイメージ）
- **サブネット**: VPCの中のさらに小さい区画。「パブリックサブネット（外部から到達可能）」「プライベートサブネット（外部から直接到達不可）」などの単位で使う

このプロジェクトでは「EC2とRDSは同じパブリックサブネットに置く」という方針までを基本設計で決め、CIDR（IPアドレス範囲）などの細部は実装フェーズで決める、としている（§7）。理由は、コスト・セキュリティに影響する構造的な決定（NAT Gateway/ALBを使わない、EC2とRDSを同じサブネットに置く）はすでに固まっており、具体的な数値はどの値を選んでも構造に影響しないため。

## EC2 / RDSのmicroクラス

- **EC2**: 仮想サーバー1台分
- **RDS**: AWSが管理してくれるDBサーバー
- **microクラス**: CPU・メモリが最小のプラン。t2.micro/t3.microなどはAWSアカウント作成後一定期間無料になる対象なので、これを選ぶことでコストを抑えている。ただし無料枠の対象インスタンスタイプはAWSアカウントによって異なる（本プロジェクトでは、実際にTerraformで構築する際にt2.microが無料枠対象外と判明し、t3.microに変更した）。`aws ec2 describe-instance-types --filters Name=free-tier-eligible,Values=true` で自分のアカウントの対象を確認できる

## デプロイ

書いたコードを、実際にユーザーが使えるサーバー（このプロジェクトではEC2）に反映させる作業のこと。GitHubにpushしただけでは、本番のEC2上のアプリは古いままなので、別途デプロイの作業が必要。

このプロジェクトでの手順（§10）:
1. EC2にSSH接続する
2. 最新コードをpull（またはDockerイメージをビルド）する
3. `docker compose up -d --build` でコンテナを再起動する

## CI/CD

- **CI（継続的インテグレーション）**: pushのたびに自動でテストなどを実行する仕組み
- **CD（継続的デリバリー/デプロイ）**: テスト後、自動で本番環境に反映する仕組み

このプロジェクトでは、GitHub Actionsで**テストは自動実行**するが、**デプロイは自動化せず手動**で行う方針にしている（§10）。理由は、pushのたびに自動でEC2へ反映すると、動作確認中の未完成な変更がそのまま本番に出てしまうリスクがあるため。
